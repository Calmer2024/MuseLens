## 三、核心设计取舍

### 1. 透镜市场没有直接复用 `lenses` 表

这是本次最重要的设计取舍之一。

当前后端已经把 `lenses` 表用于：

- 运行时 Lens 注册表
- Router / Retrieval / Planner / Compiler 的能力目录

如果直接把数据库设计文档中的“透镜市场”也落到同一个 `lenses` 表，会和现有运行时能力目录产生语义冲突，风险很高。

因此本次实现采用了单独的市场表：

- `market_lenses`
- `market_lens_versions`
- `user_lenses`
- `lens_favorites`
- `lens_reviews`

这样做的好处是：

- 不会破坏现有运行时 Lens 编排能力
- 不会影响已经完成的 Router / RAG / 注册表逻辑
- 后续若要做“市场透镜安装后映射为运行时 Lens”的桥接层，也更清晰

### 2. PostgreSQL 优先，SQLite 保持测试兼容

本次新增模块全部采用了“PostgreSQL 优先、SQLite 测试兼容”的做法。

原因是：

- 正式环境需要 PostgreSQL
- 单元测试继续依赖 SQLite 内存库会更快、更稳

因此本次新增表字段时：

- PostgreSQL 下优先使用合适类型
- SQLite 下允许同一套 ORM 正常建表与测试

### 3. 用户密码采用标准库 PBKDF2 哈希

为了避免额外引入复杂鉴权依赖，本次用户密码处理使用了 Python 标准库实现：

- `hashlib.pbkdf2_hmac`

这样可以做到：

- 注册时生成密码哈希
- 登录时校验密码
- 不在数据库中存明文密码

这满足当前阶段的后端基础安全要求。
