# 树状资产层设计

不再是简单的"图片列表 + 撤销栈"，而是"有版本意识的非破坏性编辑历史管理器"

- 分支逻辑是"从任意节点衍生新版本"，而不是只支持线性撤销/重做
- 查询策略是"路径数组 O(1) + 递归 CTE 按需"，而不是每次都扫全表
- 与数据库深度结合，并考虑未来节点数量很多、多轮编辑迭代的情况

---

## 一、整体分层：把"存储、操作、查询"拆开

建议把树状资产能力拆成 3 层，各自职责清晰：

**1. 数据层（4 张表）**
- `projects`：树的根容器，持有两个关键引用：`root_node_id`（不变的原图根节点）和 `current_node_id`（用户当前编辑位置，随操作流动）
- `asset_nodes`：树中每一个图片版本，存储图片 URL、生成参数、`depth`（深度）、`path_json`（从根到自身的完整 ID 路径数组）
- `asset_edges`：连接父子节点的有向边，记录从父图到子图所用的透镜 ID、参数字典、用户 prompt、执行耗时
- `node_tags`：节点上的语义标签（颜色+文字，如"最终版"/"客户审核"）

**2. 服务层（asset_tree_service）**
- 封装所有写操作：创建项目、添加根节点、创建子节点（含同步维护 `path_json`/`depth`/统计字段）、删除节点/子树
- 封装所有查询操作：完整树结构、祖先路径、后代列表、节点对比
- 保证树结构一致性：调用方只需传入业务参数，不需要关心 `path_json` 维护、`node_count` 更新等内部细节

**3. API 层（asset_tree 端点）**
- 职责变得更清晰：只做"参数校验 + 调用服务层 + HTTP 错误映射"
- 不直接操作数据库，不实现任何树遍历逻辑
- 统一前缀：`/api/v1/asset-tree`

## 二、核心数据抽象

### 1. Project — 树的根容器

Project 是树的"配置文件"，本身不存图片，只持有两个动态指针：

- `root_node_id`：创建根节点后赋值，此后**不再改变**
- `current_node_id`：随着用户的每次操作（创建子节点、手动切换）更新，用于恢复编辑器状态

附带两个计数字段，避免前端频繁 COUNT 查询：

- `node_count`：每次 `add_root_node` / `create_child_node` / `delete_node` 时同步累加/递减
- `branch_count`：当某个父节点的出度从 1 增加到 2 时 +1（即"新产生分叉"时才计数，而不是节点总数）

### 2. AssetNode — 图片版本

AssetNode 代表树中一个可交互的"图片快照"，关键字段：

- `image_url` / `thumbnail_url`：完整图和缩略图，均为外部存储 URL（MinIO / 本地路径），数据库只存引用
- `node_type`：`original`（用户上传的原图）/ `generated`（AI 生成）/ `uploaded`（参考图）
- `muse_dna_json`：生成该节点时所用的完整 DAGBlueprint 快照，确保未来可以精确复现
- `generation_params_json`：精简的参数摘要，用于前端"参数信息面板"展示，无需反序列化 MuseDNA

**关键设计：`depth` + `path_json`**

```
根节点 (depth=0):  path_json = ["root_id"]
子节点 (depth=1):  path_json = ["root_id", "child_id"]
孙节点 (depth=2):  path_json = ["root_id", "child_id", "grandchild_id"]
```

写入时 `path = parent.path + [self.node_id]`，代价 O(1)；
查询祖先路径时直接读取 `path_json`，用 ID 列表批量 SELECT，代价 O(depth)，**无需递归遍历**。

- `status`：`generating`（异步生成中）/ `completed`（已完成）/ `failed`（失败）——支持"先占位再回填"的异步写入模式

### 3. AssetEdge — 操作边

边的存在使"这张图是怎么来的"变得可追溯。关键字段：

- `source_node_id` / `target_node_id`：构成有向边，`UNIQUE(source, target)` 约束确保同一对父子之间只有一条边
- `lens_id`：引用 `lenses` 表；同时冗余存储 `lens_name`，防止透镜被删除后无法追溯历史
- `user_prompt`：用户原始自然语言指令，是"这次操作是什么意图"的最直观记录
- `parameters_json`：本次实际传入的参数值（区别于 MuseDNA 中的完整 workflow 定义）
- `execution_time_ms`：ComfyUI 实际耗时，用于性能统计和前端展示

约束：`CHECK(source_node_id != target_node_id)` 禁止自环，保证树是 DAG。

### 4. NodeTag — 节点标签

轻量级语义标注。`label`（文字）+ `color`（HEX 颜色）构成一个视觉标签，用于在树可视化中高亮标注重要版本。一个节点可以有多个标签，无上限。

## 三、树操作的输入/输出抽象（服务层接口）

树状资产服务对外暴露若干原子操作，调用方只需关心业务字段，内部维护由服务层封装：

**写操作**

`create_project(db, name, description)` → `Project`
- 创建空项目，此时无根节点，`root_node_id = NULL`

`add_root_node(db, project_id, image_url, ...)` → `AssetNode`
- 幂等限制：每个项目只能调用一次；重复调用抛 `ValueError`
- 成功后同步更新 `project.root_node_id`, `current_node_id`, `cover_url`, `node_count = 1`

`create_child_node(db, project_id, parent_node_id, image_url, lens_id, user_prompt, parameters, ...)` → `(AssetNode, AssetEdge)`
- 核心写入操作，一次调用同时产出节点+边
- 内部自动推导 `depth = parent.depth + 1`，`path = parent.path + [new_id]`
- 更新 `project.current_node_id` 和 `node_count`；若父节点此前已有子节点，则 `branch_count += 1`

`delete_node(db, node_id, cascade=False)` → `bool`
- `cascade=False`：只允许删除叶节点（出度为 0），否则抛 `ValueError`
- `cascade=True`：级联删除以该节点为根的整棵子树（含所有后代节点、边、标签）

**查询操作**

`get_project_tree(db, project_id)` → `{project, nodes[], edges[]}`
- 一次查询返回完整图结构，供前端 D3.js / Cytoscape.js 直接渲染

`get_node_ancestors(db, node_id)` → `{ancestors[], path_edges[]}`
- 利用 `path_json` 字段，O(1) 定位所有祖先 ID，再批量查询节点详情和路径边

`get_node_descendants(db, node_id)` → `{descendants[]}`
- 使用递归 CTE 遍历 `asset_edges`，返回所有后代节点（不含自身）

`compare_nodes(db, node_a_id, node_b_id)` → `{node_a, node_b, edge?}`
- 返回两节点的完整信息；若 a→b 之间存在直接边，一并返回边的操作详情

## 四、核心操作详解：`create_child_node` 全流程

这是整个模块中最关键的写入操作，一次调用需要完成 5 件事：

```
1. 校验：project 存在 & parent_node 存在且属于该 project
          ↓
2. 读取：parent.depth、parent.path_json（用于推导新节点的位置信息）
          ↓
3. 写入 AssetNode：
     depth     = parent.depth + 1
     path_json = parent.path + [new_node_id]
     status    = "generating"（可选，支持异步模式）或 "completed"
          ↓
4. 写入 AssetEdge：
     source = parent_node_id
     target = new_node_id
     lens_id / lens_name / user_prompt / parameters_json / ...
          ↓
5. 更新 Project：
     current_node_id  = new_node_id
     node_count      += 1
     branch_count    += 1（仅当 parent 此前已有子节点，即出度从 1→2 时）
```

全程在同一个 `db.commit()` 内完成，保证原子性。

**异步生成模式**（ComfyUI 耗时较长时）：

```
调用方先调用 create_child_node（status="generating", image_url 为占位符）
              ↓
       ComfyUI 执行完成
              ↓
调用方再调用 update_node_status（status="completed", image_url=真实URL）
```

这样前端可以立即在树上看到一个"生成中"的占位节点，避免等待感。

## 五、查询机制：两种策略的选型

树结构查询面临两个方向的问题：**向上找祖先**和**向下找后代**，采用不同策略：

**向上找祖先 → path_json 字段（O(1) 定位）**

- 祖先查询最常见场景：面包屑导航、重新生成时还原操作序列
- 写入时已经把完整路径数组存入 `path_json`，查询时直接用 `IN (path_ids)` 批量取数，不扫 `asset_edges`
- 代价：每次创建子节点时序列化写入 path_json（但这是 O(1) 操作，代价极低）

**向下找后代 → 递归 CTE（按需遍历）**

- 后代查询主要用于"级联删除"和"统计某分支的节点数"，频率相对低
- 使用 SQLite 3.35+ 原生支持的递归 CTE：
  ```sql
  WITH RECURSIVE subtree(node_id) AS (
      SELECT :root_id
      UNION ALL
      SELECT ae.target_node_id
      FROM asset_edges ae
      JOIN subtree st ON ae.source_node_id = st.node_id
  )
  SELECT node_id FROM subtree WHERE node_id != :root_id
  ```
- 不在 `asset_nodes` 上维护"父节点 ID"字段，由 `asset_edges` 统一表达拓扑关系，避免冗余

**整棵树渲染 → 两表直接全量查询**

- 前端渲染树时需要所有节点和所有边，直接 `SELECT * FROM asset_nodes WHERE project_id = ?` 和 `SELECT * FROM asset_edges WHERE project_id = ?`
- 一次项目的树通常不超过几十至数百节点，全量读取代价可接受
- 如果节点数量极多（100+），可以增加"懒加载"接口：先返回节点骨架（`node_id`+`depth`），前端请求视口内节点的缩略图

## 六、与其它模块之间的"契约（数据结构）"

### 1. 编排层 → 树状资产层

编排层（Editor / Router / 任务调度器）在 ComfyUI 生成完成后，调用以下接口将结果写入资产树：

- 请求（创建子节点）：
  - `project_id`：string
  - `parent_node_id`：string（用户点击的那个节点）
  - `image_url`：string（生成图已上传至存储后端的 URL）
  - `thumbnail_url`：string
  - `lens_id` / `lens_name`：string
  - `user_prompt`：string（来自 Router 层的 DAGBlueprint 中的原始 prompt）
  - `parameters`：dict（透镜参数绑定值）
  - `muse_dna`：dict（完整 DAGBlueprint 快照，原样存入）
  - `execution_time_ms`：int
  - `task_id`：string（关联到任务队列的 task_id，便于排查）

- 响应：
  - `node`：完整 AssetNode（含新分配的 `node_id`）
  - `edge`：完整 AssetEdge

编排层无需关心 `depth`、`path_json`、`node_count` 的维护，这些由树状资产服务层内部处理。

### 2. 树状资产层 → 前端（渲染协议）

前端拿到 `/projects/{id}/tree` 的响应后，直接用 `nodes` 和 `edges` 构建图：

- `nodes[]` 中每个节点：
  - `node_id`：图的顶点 ID
  - `thumbnail_url`：缩略图（节点视觉主体）
  - `depth`：用于树形布局的层次信息
  - `status`：`generating` 时节点显示为加载动画
  - `tags[]`：节点上附加的彩色标签

- `edges[]` 中每条边：
  - `source_node_id` / `target_node_id`：连线的两端
  - `user_prompt`：显示在边上的操作文字（点击可展开对比视图）
  - `lens_name`：辅助显示（操作类型）

### 3. 树状资产层 → 对话/Router 层（历史上下文）

Router 层在构造 Planner 输入时，可以从树状资产层获取"当前节点的操作历史"，即祖先路径上的所有边的 `user_prompt + lens_name + parameters`，将其作为 `lens_history` 注入 SessionState：

```
GET /api/v1/asset-tree/nodes/{current_node_id}/ancestors
→ path_edges[].user_prompt + lens_name
→ 注入 Planner 的 session_context.lens_history
```

这样 Planner 能感知到"用户已经做过哪些操作"，避免重复推荐相同透镜，并在追问时利用历史上下文给出更精准的建议。

## 七、`current_node_id`：编辑器状态持久化

Router 层在处理用户请求时，需要知道"用户当前在哪个节点上编辑"，以便：

- 将该节点的 `image_url` 作为 `base_image` 传给 ComfyUI
- 将该节点的 MuseDNA 和参数历史注入 Planner 上下文

`current_node_id` 在 `projects` 表中持久化，在以下场景下更新：

| 触发操作 | 更新逻辑 |
|---------|---------|
| `add_root_node` | `current_node_id = root_node_id` |
| `create_child_node` | `current_node_id = new_node_id`（自动切换到最新生成的节点） |
| `switch_current_node`（用户手动点击树中旧节点） | `current_node_id = selected_node_id` |
| `delete_node`（删除的正好是 current_node） | `current_node_id` 回退到 `root_node_id` |

`current_node_id` 是"最后一次操作的节点"，但用户可以随时通过点击树中任意节点调用 `switch_current_node` 来切换，实现**从任意历史版本重新出发**的非破坏性编辑。

## 八、扩展性：深度限制、删除策略、未来迁移

### 1. 节点数量多时

- 服务层：所有写操作已使用索引字段（`project_id`、`source_node_id`、`target_node_id`）进行过滤，O(N) 全表扫描只发生在 `get_project_tree` 的全量读取，正常项目节点数不超过几百个
- 建议增加"最大深度"校验（建议上限 20 层）：在 `create_child_node` 中检查 `parent.depth + 1 <= MAX_DEPTH`，超出时拒绝写入
- 未来节点数极多（1000+）时：可在 `asset_nodes` 增加 `parent_node_id` 冗余字段加速直接父子查询，`get_project_tree` 改为分页懒加载

### 2. 多轮编辑迭代

- `path_json` 已经保留了完整的操作路径，Planner 可以读取祖先路径上所有边的 prompt + 参数，感知用户的"编辑意图演化"
- `project.current_node_id` 是 Planner 每轮构造上下文时的出发点，不需要 Router 层自己维护"用户在哪"的状态

### 3. 迁移至 PostgreSQL

当前所有 JSON 字段以 `TEXT` 存储（SQLite 兼容），迁移时的变更点：
- `muse_dna_json`, `parameters_json`, `path_json` 等字段改为 `JSONB` 类型
- `path_json` 改为原生 `UUID[]` 数组，支持 GIN 索引加速路径查询
- 添加数据库触发器替代服务层的 `node_count` 手动维护
- 服务层的 `json.loads` / `json.dumps` 调用可以全部移除

## 九、总结实现要点

- **树状资产服务本身只做"数据读写 + 结构一致性维护"**：
  - 所有"何时生成、调哪个透镜、生成什么"由编排层（Router/Editor）决定
  - 树状资产服务只管"把结果正确地写进树里，并提供结构化的查询接口"

- **两种查询策略的组合使用**：
  - `path_json` → 向上找祖先，O(1) 定位，高频使用
  - 递归 CTE → 向下找后代，按需遍历，低频使用（主要用于级联删除）

- **`current_node_id` 是编辑器与数据库之间的唯一锚点**：
  - Router 层每次处理请求前读取 `project.current_node_id`，获取当前 `base_image` 和操作历史
  - 用户在树上点击节点时调用 `switch_current_node`，同步持久化状态

- **与编排层的契约只有一个核心接口**：`create_child_node`
  - 输入：`parent_node_id + image_url + lens信息 + prompt + 参数 + MuseDNA`
  - 输出：新节点 + 新边（`node_id` 是后续操作的锚点）
  - 返回后立即更新 `current_node_id`，下一次 Router 请求自动感知

- **节点删除策略对树结构影响最大，需明确约束**：
  - 非叶节点不允许非级联删除，防止孤儿节点污染 `path_json`
  - 级联删除通过递归 CTE 一次性找出全部后代，批量删除，同步修复 `project` 统计字段
